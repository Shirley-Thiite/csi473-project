ADR-002: Framework, Patterns and Interface Boundaries

Project: Campus Lost and Found Management System
Team: CSI473 Team 12
Date: 9 October 2026
Branch: lab-09
Status: Accepted

1. Context

ADR-001 selected Alternative A: a modular monolith with an event-sourced audit log. That decision established the overall structure of the system, the separation of the primary database, the event store, and the encrypted blob store, and the module boundaries. It did not establish the detailed design of the core workflow, the patterns that would implement the module boundaries, or the framework choices that would support them.

Lab 09 requires us to refine the architecture into implementable responsibilities and interfaces, using patterns only where they solve a named project problem. This ADR records the patterns we selected, the patterns and technologies we rejected, and the framework and dependency-management decisions that support them. It is consistent with docs/pattern-decisions.md, docs/framework-decision.md, and models/detailed-class-design.puml.

2. Decision

We will implement the core workflow using three patterns and two interface boundaries:

- Repository pattern for the persistence boundary. The Report module and the Claim module depend on ItemRepository, CustodyRepository, EvidenceRepository, and UnitOfWorkinterfaces. Concrete adapters (PostgresItemRepository, EventStoreCustodyRepository, EncryptedBlobEvidenceRepository, PostgresUnitOfWork) implement these interfaces and are injected at startup. The CustodyRepositoryinterface exposes only appendand findByItemId, with no update or delete methods.

- Adapter pattern for external systems. The Auth module depends on an IdentityProviderinterface. The Notification module depends on an EmailSenderinterface. Concrete adapters (UniversityOidcAdapter, SmtpEmailAdapter) implement these interfaces and are the only classes that know the external APIs. FakeIdentityProviderand FakeEmailSenderare used in tests.

- Factory Method for Item creation. The ItemFactoryhas two methods, createFoundItemand createLostItem, each guaranteeing the correct initial status and report type for the report path. There is no general-purpose Item constructor exposed to callers.

- State pattern for status transitions. Each status (LOST, FOUND, RESOLVED) is represented by a state class that knows which transitions are allowed from it and produces a ChainOfCustodyEntrywhen a transition occurs. The Item delegates transition requests to its current state.

We will use a lightweight backend framework without an integrated ORM for the event store, a relational database for both the primary database and the event store, server-rendered responsive views for the frontend, and an OIDC client library behind the IdentityProvideradapter.

We explicitly reject the use of a full ORM for the event store, and the use of an event bus or message queue for the secondary effects of claim decisions.

3. Alternatives Considered

3.1 Alternative: Full ORM for Both Stores

Applying a full ORM (Hibernate, Entity Framework, or equivalent) uniformly to the primary database and the event store. The ORM would provide automatic transaction management, entity mapping, and migrations.

Why rejected. A full ORM provides updateand deleteoperations by default, which conflicts with the append-only guarantee that BR-07 and QS-07 depend on. Configuring the ORM to prevent updates and deletes on a specific table is possible but fragile. A future developer could accidentally add an update method, and cascading delete behavior could remove custody entries as a side effect of deleting a related entity. The risk is not theoretical; it is a common source of integrity bugs in systems that use ORMs for audit data.

The alternative we chose is to use a lightweight query builder for the primary database and a thin database client with INSERT-only privileges for the event store.

3.2 Alternative: Direct Database Calls Without Repositories

Calling the database client directly from the Report and Claim modules, without a Repository interface between them.

Why rejected. Direct calls couple the business logic to a specific database technology and make unit testing require a running database. The failure tests from Lab 08, which simulate an event store outage, would be difficult to implement without a substitution point. The Repository pattern provides that substitution point and keeps the business logic testable.

3.3 Alternative: Observer Pattern for Secondary Effects

Publishing domain events for claim decisions and having subscribers handle the secondary effects (notification, handover record creation, custody append).

Why rejected. The number of secondary effects is small and stable, and they must happen in a well-ordered flow that preserves the transactional guarantee. An event bus would introduce asynchronous decoupling that complicates this guarantee. If the item status commits but the custody append is delivered asynchronously and fails, the system is inconsistent in a way that is not visible to the user. The operational complexity of running a message broker is also disproportionate for a semester project.

The alternative we chose is to coordinate the secondary effects synchronously in the ClaimService.decidemethod, with the notification logged and retried by a scheduled job if the email sender fails.

3.4 Alternative: Full SPA Frontend

Using a single-page application framework (React, Vue, Angular) for the frontend, with a REST API on the backend.

Why rejected. This was already considered and rejected in ADR-001. Server-rendered views are easier to make accessible and mobile-responsive, they degrade gracefully on older browsers, and they do not require a separate build pipeline or deployment. The mobile responsiveness requirement (FR-29) is satisfied by a responsive CSS framework.

3.5 Alternative: Local Authentication

A local username/password system instead of OIDC integration with the university.

Why rejected. Approval Condition 1 requires integration with the university authentication system. A local credential store would add a password management burden that the team does not want to carry, and would introduce a security surface we would have to defend without the university's support.

4. Consequences

4.1 Positive Consequences

Structural integrity guarantee. The CustodyRepositoryinterface exposes only appendand findByItemId. There is no updatemethod to call. This makes the append-only guarantee a property of the code, not a policy. Combined with the database privilege restriction (INSERT only on the event store), the guarantee is enforced at two levels.

Testability. The business logic depends on interfaces, not on concrete adapters. Tests can substitute in-memory repositories, a fake OIDC provider, and a fake email sender. The failure scenarios from Lab 08 (event store unavailable, blob store unavailable, duplicate submission) can be tested without standing up the full deployment.

External system isolation. The Adapter pattern isolates the OIDC provider and the SMTP server behind IdentityProviderand EmailSenderinterfaces. If the university changes its OIDC claim structure or a library needs to be replaced, only the adapter changes. The rest of the application continues to compile and pass its tests.

Construction safety. The ItemFactoryguarantees that every Item starts in the correct state for its report type. An invalid Item cannot exist, even transiently, because the general-purpose constructor is not exposed to callers.

Explicit transition logging. The State pattern makes it impossible to change an Item's status without producing a ChainOfCustodyEntry, because the transition method returns the entry and the interface requires it. This supports BR-07 directly.

4.2 Negative Consequences

Additional code. The Repository, Adapter, Factory, and State patterns add interfaces and classes that would not be needed in a simpler design. For a small application, this is sometimes considered over-engineering. We accept this because the audit and evidence guarantees are structural rather than procedural, and because the failure testing requirements from Lab 08 need substitution points.

Two data access mechanisms. The primary database uses a lightweight query builder or ORM, and the event store uses a thin database client. The team must understand when to use which mechanism and why the event store does not accept updates. This is a learning burden for a small team.

Longer Claim service method. The ClaimService.decidemethod coordinates multiple secondary effects synchronously. The method is longer than it would be with an event bus, and adding a new secondary effect requires modifying the method. We accept this because the number of effects is small and stable, and because synchronous coordination preserves the transactional guarantee.

Deferred Observability. By rejecting the Observer pattern, we give up the ability to add new subscribers to claim decisions without modifying the Claim module. If a future requirement needs a new secondary effect (for example, analytics or an external notification channel), we will need to modify the Claim module. We accept this as a trade-off against the complexity of an event bus.

4.3 Risks

Risk 1: Interface erosion. The Repository and Adapter interfaces are only valuable if the team keeps them. If a developer bypasses the CustodyRepositoryand calls the event store client directly to save time, the append-only guarantee is compromised. We will enforce the boundary through code review and by keeping the concrete event store client in a separate module that is not imported by the business logic.

Risk 2: State pattern growth. The State pattern is clean for three states, but if the item lifecycle grows to ten states with many transitions, the number of state classes becomes unwieldy. We will monitor the complexity and consider a table-driven approach if the state count grows beyond five.

Risk 3: Factory method duplication. The ItemFactorycurrently has two methods (createFoundItemand createLostItem). If a third report type is added, the factory grows. We will refactor to a parameterized factory if the count exceeds three.

6. Review

This ADR was reviewed by all team members on 9 October 2026. The highest design risk was identified as interface erosion (Risk 1): if a developer bypasses the CustodyRepositoryand writes directly to the event store, the append-only guarantee is compromised. The team agreed to enforce the boundary through code review, to keep the concrete event store client in a separate module, and to add a test that fails if the business logic module imports the event store client directly.

The second risk identified was the State pattern growth (Risk 2). The team agreed to revisit the state design if the item lifecycle grows beyond five states.

8. Exit Record

Pattern or interface boundary with the greatest benefit. The CustodyRepositoryinterface. It solves the problem of variable behaviour at the storage boundary by exposing only appendand findByItemId. There is no updateor deletemethod. This makes the append-only guarantee structural rather than procedural, and it makes the failure tests from Lab 08 implementable through substitution.

Cost of the decision. The interface adds a layer between the Report module and the event store. The team must maintain the interface and the adapter, and must resist the temptation to bypass the interface when writing code under time pressure.

Test that will confirm the design works. A test that attempts to call CustodyRepository.update(...)or CustodyRepository.delete(...)should fail to compile, because those methods do not exist on the interface. A test that calls CustodyRepository.append(...)and then queries the event store directly should find exactly one new row. A test that attempts to modify the appended row through the application's database credentials should be rejected by the database. A test that simulates an event store outage during a Report Found Item submission should verify that no Item row is committed.
